# Chapter 13 — Case Studies

*Every preceding chapter argued a principle; this one checks the principles against shipped systems. We tear down six public harnesses — Claude Code, OpenAI's Codex CLI, SWE-agent and its stripped-down successor mini-SWE-agent, OpenHands, Anthropic's three-agent application-development harness, and Anthropic's multi-agent research system — and ask three questions of each: what did it choose, why did it choose that, and what should a harness engineer steal from it? The systems disagree with each other in instructive ways. One bets everything on a carefully designed agent-computer interface; its own successor bets that the interface is no longer needed. One enforces safety with an OS-level sandbox; another with a permission classifier; a third with both. Read together, they map the real design space far better than any single reference architecture could.*

## How to read a harness

A harness, as Chapter 1 defines it, is everything around the model: the agent loop, the tool layer, context assembly, memory, the sandbox, permissions, verification, and observability. When you study someone else's harness, those are the load-bearing walls to find. For each system in this chapter we ask the same questions:

- **Loop:** what is one step, and what stops the loop?
- **Tools:** what can the model invoke, and how was the interface shaped for a model rather than a human?
- **Context:** what enters each model call, and what keeps the window from drowning?
- **Trust:** what is the model allowed to do without a human, and what enforces the boundary?
- **Verification:** what oracle tells the harness whether an action worked?

The systems below answer these questions differently because they serve different masters. Claude Code and Codex CLI sit in a developer's terminal, where a human is (usually) watching and the filesystem is real. SWE-agent and OpenHands were built to score on benchmarks and to be studied, so reproducibility and isolation dominate. The three-agent app-development harness and the research system run long and unattended, so verification and orchestration dominate. Keep Ledgerbot — this book's running example, the agent that triages and fixes failing CI builds in a Python monorepo — in mind as you read: it borrows from all six by the end of the chapter.

## Claude Code: the terminal harness

Claude Code is Anthropic's agentic coding environment: a CLI that reads files, runs commands, edits code, and works through problems while the developer watches, redirects, or steps away. Anthropic's [best-practices guide](https://code.claude.com/docs/en/best-practices) is unusually candid about the design pressure behind most of its features: "Claude's context window fills up fast, and performance degrades as it fills... The context window is the most important resource to manage." Almost everything distinctive about the harness — subagents, compaction, `/clear`, instruction files — is downstream of that one constraint.

**The tool layer** is small and general: file read/write/edit, shell execution, file search, and web fetch, extensible via [MCP](https://modelcontextprotocol.io/) servers. This is the opposite of the SWE-agent bet we examine below. Rather than crafting a bespoke interface per task, Claude Code hands the model roughly the same primitives a developer has and relies on model capability to compose them. The documentation encourages CLI tools (`gh`, `aws`, `sentry-cli`) over custom integrations because "CLI tools are the most context-efficient way to interact with external services" — a tool-design position Chapter 4 endorses: don't build a tool when a well-documented command already exists.

**Context delivery** runs through `CLAUDE.md`, an instruction file loaded at the start of every session. It layers: a home-directory file applies to all sessions, a project-root file is checked into git and shared with the team, a `CLAUDE.local.md` holds personal notes, and child-directory files load on demand when the agent touches those directories. The guidance on content is a compressed course in context engineering (Chapter 5): include commands the model can't guess, style rules that differ from defaults, and repository etiquette; exclude anything the model can figure out by reading code. The failure mode is documented too — "Bloated CLAUDE.md files cause Claude to ignore your actual instructions" — with a pruning test worth framing: for each line, ask whether removing it would cause mistakes; if not, cut it. The neighboring [AGENTS.md convention](https://agents.md/) — "a README for agents" supported by more than twenty tools including Codex, Gemini CLI, Cursor, and Zed, and used by over 60,000 open-source projects — shows the same idea escaping any single product and becoming infrastructure.

**Permissions** are layered rather than binary. The default mode asks before anything that might modify the system. Three mechanisms reduce the interruptions, and the documentation is honest about why they must: "After the tenth approval you're not really reviewing anymore, you're just clicking through" — the rubber-stamp problem Chapter 8 analyzes. First, explicit allowlists permit named commands (`npm run lint`, `git commit`). Second, an *auto mode* delegates review to a separate classifier model that "blocks only what looks risky: scope escalation, unknown infrastructure, or hostile-content-driven actions." Third, OS-level [sandboxing](https://code.claude.com/docs/en/best-practices) restricts filesystem and network access so the agent can act freely inside a boundary instead of asking at every step. Note the architecture: three independent mechanisms at three different trust granularities, composable rather than exclusive.

**Hooks** are the harness's determinism escape hatch. `CLAUDE.md` instructions are advisory — the model reads them and usually complies. Hooks are scripts the harness itself executes at fixed points in the loop (after a file edit, before a tool call, when the agent tries to stop), and the docs draw the line explicitly: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." A `Stop` hook can run your test suite and refuse to let the turn end until it passes (with a circuit breaker after eight consecutive blocks, so a hopeless task can't loop forever). This is the harness enforcing an oracle, not requesting one — the distinction Chapter 10 builds its argument around.

**Subagents** are context isolation, not (primarily) parallelism. A subagent runs in its own context window with its own tool allowlist, explores or reviews, and returns a summary; the reading it did never touches the parent's window. The docs pair this with fresh-context review: "A fresh context improves code review since Claude won't be biased toward code it just wrote" — self-evaluation bias, again, mitigated structurally rather than by prompting. Headless mode (`claude -p`, with JSON output formats) turns the whole harness into a Unix component you can pipe, loop over, and embed in CI, which is how the documented fan-out pattern works: generate a task list, then invoke one scoped headless session per item with `--allowedTools` restricting the blast radius.

**What to steal.** Four things. The advisory/deterministic split — write preferences into instruction files, but encode invariants as hooks the harness runs itself. The layered permission model — allowlist the known-safe, classify the ambiguous, sandbox the rest, and never rely on a human clicking "approve" forty times to stay vigilant. Subagents as a context-budget instrument. And the discipline of treating instruction files like code: reviewed, pruned, version-controlled, and tested by observing whether behavior actually shifts.

## OpenAI Codex CLI: sandbox-first

[Codex CLI](https://github.com/openai/codex) is OpenAI's terminal coding agent, open source under Apache-2.0 and implemented almost entirely in Rust (about 96% of the repository). It occupies the same niche as Claude Code but resolves the trust question differently, and the difference is the reason to study it: where Claude Code's first line of defense is a permission dialog (with sandboxing available), Codex's first line of defense is the operating system.

**Two orthogonal axes.** Codex separates *where the agent may act* from *when it must ask*, as two independent settings. The [sandbox mode](https://developers.openai.com/codex/agent-approvals-security) answers the first: `read-only` lets commands read files but write nothing; `workspace-write` permits writes inside the current workspace and temp directories, with network access disabled unless explicitly enabled; `danger-full-access` removes restrictions and wears its warning in its name. The approval policy answers the second: `untrusted` prompts for essentially everything, `on-request` lets the agent run routine reads, edits, and local commands itself and asks "only when it needs to step outside the workspace or reach the network," `on-failure` prompts only after a command fails inside the sandbox, and `never` runs without asking. The two axes compose into profiles — full-auto is `workspace-write` plus `on-request`; a quiet read-only analysis mode is `read-only` plus `never`.

This factoring is worth dwelling on, because conflating the two axes is a common harness design error. "Can the agent write to `/etc`?" and "should a human see this command before it runs?" are different questions with different failure costs. A harness that answers both with one knob forces users to choose between safety and flow. Codex's `on-failure` policy is the cleverest cell in the matrix: let the sandbox silently absorb the risk, and escalate to the human only when the sandbox itself blocked something the agent believes it needs — turning the isolation boundary into a *detection* mechanism as well as a prevention mechanism.

**OS-level enforcement.** The sandbox is not implemented by prompting the model to behave. On macOS, Codex runs commands under [Seatbelt](https://developers.openai.com/codex/agent-approvals-security) via `sandbox-exec` with a profile corresponding to the selected mode; on Linux it uses Landlock and seccomp. These are kernel-enforced mechanisms: a command that tries to write outside the workspace fails with a permission error regardless of what the model intended or what a prompt injection instructed. Chapter 7's argument — isolation is the safety model, permissioning is layered above it — is Codex's architecture stated as a principle. A jailbroken model inside `workspace-write` with network off can damage exactly one working tree, which is what version control is for.

**Configuration** flows through `AGENTS.md`, the cross-tool instruction-file format Codex helped establish, with nesting semantics for monorepos ("agents automatically read the nearest file in the directory tree, so the closest one takes precedence"). MCP support covers external tools. The Rust implementation is itself a harness decision: a single static binary with no interpreter runtime makes the sandbox setup faster and the supply chain smaller.

**What to steal.** The two-axis trust model, verbatim — most internal harnesses need exactly this factoring and instead ship one "YOLO mode" boolean. The naming convention that makes the dangerous path ugly to type (`danger-full-access`). And the principle that isolation must be enforced below the model, by the kernel or the container runtime, because everything above the model is advisory to an attacker who controls the model's inputs.

## SWE-agent: the agent-computer interface as a research result

[SWE-agent](https://arxiv.org/abs/2405.15793) (Yang, Jimenez et al., 2024) is the system that gave this book the term *ACI* — agent-computer interface — and it earns its place here by being the first rigorous demonstration that harness design, independent of model choice, moves task performance. The paper's framing is the important part: language model agents are "a distinct category of end users requiring specialized software interfaces." Humans get HCI; agents get ACI, and it deserves the same design effort.

The concrete interface decisions are the ones Chapter 4 generalizes. The **file viewer** shows 100 lines at a time — enough to see structure, small enough not to flood the context window. **Search commands** return at most 50 results and suppress overly long output; a search that would return more asks the agent to narrow the query rather than dumping ten thousand lines into history. The **edit command** integrates a linter and *rejects syntactically invalid edits* at submission time, feeding the error straight back — the agent cannot save broken Python, so an entire class of compounding failures (edit, run, misread traceback, edit the wrong thing) is deleted from the trajectory space rather than merely discouraged. Feedback is compact and informative: every command returns something the model can act on, because in an agent loop, silence is ambiguity.

The results made the case quantitatively. SWE-agent reached 12.5% pass@1 on the full SWE-bench benchmark and 87.7% on HumanEvalFix — state of the art at the time, and far above the same model operating through a plain Linux shell. Same weights, different interface, different outcome: the harness was the experimental variable. That is the paper's enduring lesson, and it is also — as the next section shows — a lesson with a shelf life.

**What to steal.** The method more than the artifact. SWE-agent treated interface design as an empirical question with an evaluation harness attached (Chapter 12's discipline): propose an interface change, run the benchmark, keep what wins. Its specific guardrails — bounded output, integrated validation, errors that teach — remain the correct defaults for any tool layer. But hold the specifics loosely, for reasons its own authors supplied a year later.

## mini-SWE-agent: the control experiment

In 2025 the SWE-agent team released [mini-SWE-agent](https://github.com/SWE-agent/mini-swe-agent), whose core agent class is about 100 lines of Python, and whose design deletes nearly everything the original paper argued for. It "does not have any tools other than bash — it doesn't even need to use the tool-calling interface of the LMs." There is no file viewer, no bounded search, no lint-guarded editor. Every step appends to a linear message history. Every command runs as an independent `subprocess.run` with no persistent shell state — which makes execution trivially portable: "switch out `subprocess.run` with `docker exec`" and the same agent runs sandboxed.

The motivating question was posed directly: "What if our agent was 100x simpler, and still worked nearly as well?" The answer, with frontier models, is that it works *better* than the original: mini-SWE-agent scores above 74% on SWE-bench Verified, roughly six times the original SWE-agent's result on the harder full benchmark. A year of model improvement had absorbed the ACI. The team's own framing of the shift is the thesis of Chapter 14 in one sentence: the simplification "puts the language model (rather than the agent scaffold) in the middle of our attention."

Read the pair of systems as a controlled study in harness staleness. Every 2024 ACI feature encoded an assumption about a 2024 model weakness: models lose track of long files (so paginate), models flood their own context (so cap results), models write syntax errors and spiral (so lint at the gate). By 2025 the weaknesses had shrunk below the threshold where the scaffolding paid rent, and the scaffolding's residual cost — constraining a stronger model to an interface designed for a weaker one — flipped the sign of its value.

Note what mini-SWE-agent *kept*: a loop, a transcript, sandboxable execution, and the SWE-bench oracle to verify against. The capability compensations went; the trust and verification machinery stayed. Keep that split in mind — Chapter 14 argues it is the general pattern.

**What to steal.** The habit of maintaining a minimal baseline harness and re-running it against your evaluation suite whenever a new model lands. mini-SWE-agent is, among other things, the SWE-agent team's null hypothesis made executable. Every harness team should own one: if your elaborate harness no longer beats your hundred-line one, your elaborations are now decoration — or drag.

## OpenHands: the platform bet

[OpenHands](https://arxiv.org/abs/2407.16741) (formerly OpenDevin; ICLR 2025, MIT-licensed, with more than 2,100 contributions from 188+ contributors) is what a harness looks like when it is built as a *community research platform* rather than a product or a paper artifact. Its agents "interact by writing code, interacting with a command line, and browsing the web," and three architectural commitments distinguish it.

**The event stream.** OpenHands structures the entire interaction as a chronological stream of *actions* (what an agent does) and *observations* (what the environment returns). The event stream is the state — agents are substantially functions from event history to next action. This is the transcript-is-ground-truth discipline of Chapter 11 promoted from logging convention to load-bearing architecture: replay, debugging, evaluation, and delegation all operate on the same durable record, and nothing important lives only in a process's memory.

**Code as action.** Following the CodeAct line of work, OpenHands collapses the action space into executable code: rather than choosing from dozens of bespoke tool schemas, the agent writes Python (in a Jupyter/IPython environment) or shell commands. The argument is expressiveness — code composes, loops, and branches, where enumerated tool calls do not. The trade-off is that everything hinges on the runtime: arbitrary code execution is only offerable inside real isolation, so OpenHands runs agent actions in a sandboxed Docker runtime, with the browser and interpreter behind the same boundary. This is Chapter 4's consolidation-versus-proliferation tension resolved at the far consolidation end, and Chapter 7's isolation prerequisite honored as a hard dependency.

**An agent abstraction and delegation.** The agent itself is a thin, swappable component behind a common interface, published to a shared AgentHub; agents can delegate subtasks to other specialized agents. Combined with an evaluation suite spanning 15 benchmarks — from SWE-bench for software engineering to WebArena for web interaction — the platform makes agents comparable: same runtime, same event stream, same oracles, different brains. That is the eval-harness lineage of Chapter 2 applied to agent research itself.

**What to steal.** The event-sourced core — if you adopt one OpenHands idea, make your harness's single source of truth an append-only action/observation log and derive everything else from it. Second, the honest coupling: if you want code-as-action's expressiveness, you must pay for real sandboxing; OpenHands never pretends otherwise. Third, the separation of agent from runtime as a swappable interface, which is what lets one team's harness evaluate many teams' agents.

## Anthropic's three-agent app-development harness

Anthropic's engineering post on [harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps) documents a harness that turns a one-to-four-sentence prompt into a working full-stack application over hours of unattended operation. Its architecture is the planner/generator/evaluator pattern Chapter 9 presents, and the post is valuable because it explains *which model failure each agent exists to compensate*.

The **planner** expands the user's brief prompt into an ambitious multi-sprint product specification — high-level design, not granular implementation. The **generator** implements sprint by sprint against a standard stack. The **evaluator** is the interesting one: it drives the *running application* through Playwright browser automation, "like a user would," and grades pass/fail against predefined criteria. Not code review — behavioral verification against the real artifact, in a fresh context that never saw the generator's reasoning.

The evaluator exists because of **self-evaluation bias**. Asked to grade their own work, the post reports, "agents tend to respond by confidently praising the work — even when, to a human observer, the quality is obviously mediocre." Separating generation from evaluation proved more tractable than making the generator self-critical — the same conclusion Chapter 10 reaches, and the same one Claude Code's fresh-context review pattern and the research system's separate judge embody. Three independent teams, one convergent design: the worker must not grade itself.

**Sprint contracts** solve the handoff problem. Before implementation, generator and evaluator negotiate an explicit agreement defining "done" for the chunk of work — testable success criteria fixed *before* coding begins. Without the contract, the evaluator grades against its own guess of the intent and the generator argues with the grade; with it, verification is mechanical. This is Chapter 9's files-over-chat handoff discipline: agents coordinate through durable artifacts, not vibes.

The post also names **context anxiety**: Claude Sonnet 4.5 would prematurely wrap up work as its context window filled — a model *behavior*, not a token-limit error, and one the sprint decomposition partly existed to manage. And then, most unusually for an engineering post, it documents its own obsolescence: when Opus 4.6 arrived, the author stripped the sprint decomposition entirely — the generator "ran coherently for over two hours without the sprint decomposition that Opus 4.5 had needed" — and moved per-sprint evaluation to a single end-of-build check. The stated moral: "every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing, both because they may be incorrect, and because they can quickly go stale as models improve." Chapter 14 takes that sentence as its epigraph in spirit.

**What to steal.** Behavioral end-to-end verification as the oracle — grade the running system, not the diff. Negotiated, written definitions of done before generation starts. And the practice of dating your scaffolding: record *why* each component exists (which model, which weakness) so that when the model changes, you know exactly what to re-test.

## A deep-research harness: fan-out, verify, synthesize

The last teardown is a different species: not a coding agent but Anthropic's [multi-agent research system](https://www.anthropic.com/engineering/built-multi-agent-research-system), the harness behind Claude's Research feature. It is the clearest published example of the orchestrator-workers pattern (Chapter 9) deployed in production, and the most quantified.

**The shape.** A lead agent (Claude Opus 4, in the published configuration) analyzes the query, develops a strategy, and spawns subagents (Claude Sonnet 4) that search in parallel, each in its own context window, each exploring a different aspect. Findings flow back; the lead synthesizes, decides whether more research is needed, and iterates; a dedicated CitationAgent then locates sources for every claim. Fan out, verify, synthesize. The design exists because research is breadth-shaped: the corpus of relevant material exceeds any single context window, and independent lines of inquiry are genuinely parallel. Subagents provide "separation of concerns" — distinct tools, prompts, and trajectories reduce path dependency — and, bluntly, more total context: distributing work across windows "add[s] capacity for parallel reasoning."

**The economics are the headline.** The multi-agent configuration outperformed single-agent Opus 4 by 90.2% on internal research evaluations — and consumed about 15× the tokens of a chat interaction (single-agent research runs about 4×). On the BrowseComp evaluation, "token usage by itself explains 80% of the variance" in performance. The post draws the sober conclusion every orchestration chapter should end with: "Multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance." Multi-agent is not an architecture upgrade; it is a purchase. The post is equally clear about poor fits: domains needing shared context across agents or tight coordination — "most coding tasks" — do not repay the spend.

**Delegation is a prompt-engineering problem.** Early lead agents spawned subagents with vague instructions and got duplicated or drifting work. The fixes were explicit task descriptions (objective, output format, tool guidance, boundaries) and *effort-scaling rules* embedded in the prompt: one agent for a simple fact-check, 2–4 for a comparison, 10+ for genuinely complex research. Tool descriptions mattered enough that having Claude itself test and rewrite them cut task completion time for future agents by 40% — the tool-iteration loop of Chapter 4, run by the agent.

**Verification and reliability.** Output quality is graded by an LLM judge with a rubric — factual accuracy, citation accuracy, completeness, source quality, tool efficiency — scored in a single call, supplemented by human evaluation that caught what the judge missed (subagents preferring SEO-optimized content over authoritative sources). Operationally, the system is engineered as the distributed system Chapter 11 says every long-running harness becomes: durable execution with error resumption, full production tracing to debug non-deterministic failures, and "rainbow deployments" that shift traffic gradually so a code update never strands an agent mid-session.

**What to steal.** The effort-scaling rules — explicitly telling the orchestrator how much parallelism a task class deserves is cheap and prevents both under- and over-spending. The delegation contract (objective, format, tools, boundaries) as the minimum viable subagent prompt. The rubric-based judge with human spot-checks layered above it. And the cost honesty: measure tokens per solve, and let the 15× number veto architectures the demo made look free.

## What the teardowns agree on

Six systems, three vendors, two research communities — and beneath the disagreements, a consensus worth stating plainly.

**Verification is the spine.** Every system that runs unattended built an oracle: SWE-bench's test suites, the evaluator agent's Playwright runs, the research system's citation-and-rubric judge, Claude Code's Stop hooks and its documentation's first commandment ("Give Claude a way to verify its work"). And every system that grades quality does it in a context that did not produce the work.

**Isolation is enforced below the model.** Seatbelt and Landlock, Docker runtimes, sandboxed execution behind `subprocess.run`-shaped seams. No production harness in this chapter trusts instructions to contain an agent; instructions shape behavior, kernels bound it.

**Context is managed structurally, not heroically.** Subagents, event streams, bounded tool output, instruction files with pruning discipline, fresh contexts for review — the winning systems design the window's contents rather than pleading with the model to cope.

**And the capability layer is the perishable layer.** The ACI dissolved into bash. Sprint decomposition was deleted in a model upgrade. The systems that aged best factored their harnesses so the trust and verification machinery could outlive the compensations. Why that pattern holds — and what it means for your job — is Chapter 14.
