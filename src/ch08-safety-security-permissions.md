# Chapter 8 — Safety, Security, and Permissions

*Chapter 7 built the walls; this chapter decides what passes through them. Agents fail in a security-relevant way for one root reason: a language model cannot reliably distinguish the instructions it should follow from the data it should merely process. That single weakness — prompt injection — combines with agent capabilities to produce what Simon Willison calls the lethal trifecta: private data, untrusted content, and an exfiltration channel in one system. This chapter covers the attack and the published design responses, then turns to the machinery a harness engineer actually builds: permission systems with allow/ask/deny rules, auto-approval classifiers, human-in-the-loop review that people don't rubber-stamp, trust boundaries between cooperating agents, the supply-chain risk of the tool and MCP ecosystem, and the audit logging that makes any of it accountable after the fact.*

## Instructions and data share a channel

In September 2022, researcher Riley Goodside demonstrated that GPT-3 could be steered off its task by adversarial text placed in its input — "ignore the above directions and…" — and Simon Willison [named the class of attack days later](https://simonwillison.net/2022/Sep/12/prompt-injection/): *prompt injection*, by deliberate analogy to SQL injection. Both attacks exploit a system that concatenates trusted instructions and untrusted input into one channel and then executes the result. The analogy also marks where the two diverge, and the divergence is the whole problem. SQL injection has a complete fix — parameterized queries, a hard syntactic boundary between code and data. Prompt injection has no equivalent, because a language model consumes everything as tokens in one context window; there is no architectural boundary that reliably prevents the model from treating a string it read as an instruction to follow. The UK's National Cyber Security Centre makes the point bluntly in ["Prompt injection is not SQL injection"](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection): the mitigation playbook that closed SQL injection does not transfer, and systems must instead be designed so that a successful injection has bounded consequences.

Two variants matter for harness design. *Direct* injection — a user typing adversarial instructions — is largely a content-policy problem for the model vendor. *Indirect* injection is the harness engineer's problem: the adversarial instructions arrive in material the agent was legitimately asked to process. Ledgerbot, this book's running example — an agent that triages and fixes failing CI builds in a Python monorepo — reads build logs, test output, commit messages, issue threads, and dependency changelogs. Every one of those is attacker-influenceable to some degree. A test that prints a crafted string writes into Ledgerbot's context. A dependency's release notes, fetched to explain a version bump, write into Ledgerbot's context. In the vocabulary of this book, tool results are context, and context is instructions to a system that cannot tell the difference.

It is tempting to hope the model will just get better at telling the difference. The empirical record says: partially, and not reliably. Willison's [long-running series on prompt injection](https://simonwillison.net/series/prompt-injection/) documents attack after attack against production systems from every major vendor. Detection-based defenses — classifiers that screen inputs for injection attempts — help, but as Willison notes, vendors advertising that guardrails catch "95% of attacks" are describing a failing grade in a security context: an adaptive attacker gets to keep trying until they find the 5%. The working assumption for a harness engineer must be that *some* injected instruction will eventually be followed. Security then comes from what the agent is able to do when that happens — which is an environment and permissions question, not a model question.

## The lethal trifecta

In June 2025, Willison distilled the worst-case combination into a memorable triad. [The lethal trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) is present when a single agent system combines:

1. **access to private data** — source code, email, credentials, customer records;
2. **exposure to untrusted content** — anything an attacker can write into what the agent reads;
3. **the ability to externally communicate** — any channel through which data can leave: HTTP requests, email, a public PR, even a crafted URL in rendered output.

With all three present, the attack writes itself: the untrusted content instructs the agent to gather the private data and send it out through the available channel. The model, as Willison puts it, will "happily follow *any* instructions that make it to the model, whether or not they came from their operator." No leg of the trifecta is dangerous alone. An agent that reads the open internet but holds no secrets has nothing to leak. An agent with secrets but no untrusted input has no attacker in the loop. An agent with both but no egress can be manipulated into staging data it has no way to deliver — this is why Chapter 7 treats `--network none` and egress proxies as load-bearing safety controls rather than mere hygiene.

Run Ledgerbot through the checklist. Private data: the monorepo itself, plus whatever secrets leak into CI environments — and something does, in most real CI setups. Untrusted content: build logs and test output, which any contributor (or any dependency) can influence. External communication: Ledgerbot opens pull requests, and a PR body on a public repository is a perfectly good exfiltration channel. All three legs, in the default design. The fix is not to abandon the product but to break the combination *per phase*: the phase that reads untrusted logs runs without credentials and without network; the phase that pushes a branch runs through an authenticating proxy that will deliver a diff to one repository and nothing else; and secrets are never mounted where log-reading happens. The trifecta is a design checklist you run against each execution context in the system, not against the system as a whole.

Willison flags one more thing that should shape harness policy: the risk compounds when users mix and match tools from different sources, because a tool catalog assembled ad hoc will combine all three legs without anyone deciding to. That is a direct critique of how MCP is commonly used, and we return to it in the supply-chain section.

### Case study: the GitHub MCP data heist

The clearest public demonstration of the trifecta in the wild came from Invariant Labs in May 2025. Their [GitHub MCP exploit](https://invariantlabs.ai/blog/mcp-github-vulnerability) targeted a common setup: a user runs an MCP client (Claude Desktop, in the demonstration) connected to the official GitHub MCP server with a broadly scoped token. The attacker files an issue on the user's *public* repository containing injected instructions. Later, the user innocently asks their agent to "have a look at the open issues." The agent reads the malicious issue (untrusted content), follows its instructions to pull data from the user's *private* repositories (private data, reachable because the token spans all repos), and exfiltrates it by opening a pull request on the public repository (external communication) — where the attacker, and everyone else, can read it.

The instructive part is Invariant's diagnosis: this is not a bug in the GitHub MCP server, and it "cannot be resolved through server-side patches." Every component behaved as designed; the *composition* was the vulnerability. Their proposed mitigations are harness-level: least-privilege tokens, and policy such as one-repository-per-session so that no single agent context can span the public/private boundary. When your system's security depends on which tools are mounted together in one context, security review has to happen at the harness layer — no amount of auditing individual tools will find it.

## Designing out the trifecta

If injection cannot be prevented, it can be made unprofitable. Two lines of published work show what principled — rather than probabilistic — defense looks like.

The first is ["Design Patterns for Securing LLM Agents against Prompt Injections"](https://arxiv.org/abs/2506.08837) (Beurer-Kellner et al., 2025), a collaboration across IBM, Invariant Labs, ETH Zurich, Google, and Microsoft that Willison [summarizes approvingly](https://simonwillison.net/2025/Jun/13/prompt-injection-design-patterns/). Its six patterns share one idea: once an agent has ingested untrusted content, constrain what it can subsequently do. *Action-Selector* lets the model choose from fixed actions but never process tool output. *Plan-Then-Execute* freezes the plan — which tools will be called, in what order — before any untrusted data is read, so injected text can corrupt arguments but not control flow. *LLM Map-Reduce* fans out untrusted documents to isolated per-document calls whose outputs are schema-constrained before aggregation. *Dual LLM* splits the system into a privileged model that has tools but never sees untrusted content, and a quarantined model that sees untrusted content but has no tools, exchanging data only by reference — the privileged side manipulates opaque handles like `$EMAIL_SUMMARY_1` and never the text itself. *Code-Then-Execute* has the model write a program which then runs over the data, moving the reasoning out of injection's reach. *Context Minimisation* simply keeps untrusted content out of contexts that don't need it. The paper's honest conclusion is that these buy provable properties only for *application-specific* agents; a fully general agent that reads anything and can do anything remains unsecurable by construction.

The second is Google DeepMind's CaMeL — ["Defeating Prompt Injections by Design"](https://arxiv.org/abs/2503.18813) — which industrializes the Dual-LLM idea. CaMeL extracts control flow and data flow from the *trusted* user query up front, then attaches capability metadata to every value so that data derived from untrusted sources can never alter the program's control flow, and security policies checked at each tool call prevent private values from flowing to unauthorized sinks. The cost is capability: on the AgentDojo benchmark, CaMeL solves 77% of tasks with provable security, versus 84% for the undefended system. That seven-point gap is the current price of by-design security, and the honest framing for a harness engineer is that you are choosing where on that utility/security curve each part of your system sits.

Most production harnesses cannot adopt these patterns wholesale — Ledgerbot's whole job is to read untrusted logs and then act. What they *can* adopt is the layering this book has been building toward: sandbox first (Chapter 7 bounds what actions are physically possible), then permissions (this chapter's next sections bound what actions are allowed), then trifecta-aware phase design (no single context holds all three legs), with the design patterns applied selectively to the highest-risk flows.

## Permission systems: allow, ask, deny

Inside the sandbox boundary, the harness still needs policy: which tool calls proceed silently, which require a human, which are refused outright. The now-standard shape is a three-verdict rule system — **allow**, **ask**, **deny** — evaluated against each tool call before execution. [Claude Code's permission system](https://code.claude.com/docs/en/permissions) is the most thoroughly documented public implementation, and its design decisions (and documented sharp edges) generalize to any harness, so it is worth studying as a case, not as a product recommendation.

Rules name a tool, optionally scoped by a specifier:

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run test *)",
      "Bash(git commit *)",
      "Read(src/**)",
      "WebFetch(domain:docs.python.org)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(~/.ssh/**)",
      "Bash(curl *)",
      "mcp__*"
    ]
  }
}
```

Several design principles are embedded here, each earned the hard way:

**Deny wins, and precedence is fixed.** Rules evaluate deny, then ask, then allow; the first match decides, and specificity does not reorder them. A broad `Bash(aws *)` deny blocks a narrower `Bash(aws s3 ls)` allow. This is deliberately inexpressive — you cannot carve allowlist exceptions out of a deny — because an exception mechanism is a bypass mechanism, and the failure mode of an inexpressive policy language is inconvenience while the failure mode of an expressive one is a hole.

**The harness enforces; the model requests.** Claude Code's documentation states it plainly: permission rules "are enforced by Claude Code, not by the model." Instructions in a prompt or an instruction file shape what the agent *tries*; they change nothing about what the harness *permits*. Any security property that depends on the model choosing to comply is not a security property — it is exactly what prompt injection removes.

**String matching over shell commands is a minefield, so match structure, not strings.** The documented sharp edges are a catalog of lessons for anyone building their own matcher. Compound commands: a rule for `safe-cmd *` must not authorize `safe-cmd && curl evil.com`, so the matcher splits on shell operators (`&&`, `||`, `;`, `|`, newlines) and requires every subcommand to match independently. Wrappers: `timeout 30 npm test` should match an `npm test` rule, so a fixed set of process wrappers is stripped — but environment runners like `npx` and `docker exec` are deliberately *not* stripped, because `devbox run rm -rf .` executes its argument and a `devbox run *` allow would be a blank check. Argument constraints: a pattern like `Bash(curl http://github.com/ *)` intending to restrict curl to GitHub fails against flag reordering, `https://`, redirect-following, and `URL=… && curl $URL`; the documentation's own advice is to stop trying — deny `curl` and `wget` entirely and route web access through a dedicated fetch tool whose domain matching happens on a parsed hostname, not a substring. The general lesson: canonicalize into structure (parsed command lists, resolved absolute paths, extracted hostnames) and match on that, or an adversary — including an injected instruction with harness documentation in its training data — will find the encoding you didn't think of.

**Paths and domains need the same rigor.** File rules follow gitignore semantics with explicit anchors (absolute, home-relative, settings-relative), and symlinks are checked on *both* the link path and its resolved target — deny if either matches, allow only if both do — so a symlink inside an allowed directory pointing at `~/.ssh/id_rsa` is blocked. Domain rules constrain wildcards so `example.*` cannot match `example.evil.com`. These are the details that separate a permission system from a permission-shaped decoration.

**Policy must be layerable and lockable.** Rules merge from multiple scopes — enterprise-managed, user, project, session — with managed settings unoverridable and a deny at any level final. A repository's checked-in allow rules are capability grants, so they apply only after the user explicitly trusts the workspace; otherwise cloning a malicious repo would grant it permissions. And where rule syntax runs out, an escape hatch to real code (Claude Code's `PreToolUse` hooks) lets a shell script veto any call — with the crucial property that hooks can tighten but never loosen: a matching deny rule holds regardless of what a hook returns.

## Auto-approval classifiers

Static rules cover the enumerable cases. The residue — novel commands that are almost certainly fine but match no allow rule — traditionally lands on the human, which is where approval fatigue begins. The emerging third option is an **auto-approval classifier**: a model-based judge that evaluates each unmatched tool call in context and approves, denies, or escalates it. Claude Code ships this as its `auto` permission mode (a research preview at the time of writing), which "auto-approves tool calls with background safety checks that verify actions align with your request" — note the design: the classifier judges alignment between the *action* and the *user's stated intent*, not just the action in isolation, which is precisely the check that catches an injected instruction pursuing goals the user never expressed.

Classifier-gated autonomy is only defensible with three properties. First, **it must be subordinate to the rule system**: explicit deny and ask rules bind regardless of the classifier's opinion, so the human-authored floor cannot be talked through. Second, **it must fail closed**: uncertainty escalates to a prompt or a denial, never to silent approval. Third, **it needs circuit breakers outside the model entirely** — Claude Code hard-prompts on `rm -rf /` and home-directory removals even in its most permissive bypass mode, a recognition that some actions warrant a tripwire that no amount of model judgment can waive. It is also worth stating the obvious about threat models: the classifier is itself a model reading attacker-influenced text. Against accidents it is a strong control; against a sophisticated injection it is another probabilistic layer, which is why it sits *inside* the sandbox-and-rules stack rather than replacing it.

The other lever for shrinking the prompt burden is the one Chapter 7 established: substitute enforcement for approval. When OS-level sandboxing guarantees a command cannot escape declared directories or reach undeclared domains, the harness can stop asking about commands inside that boundary — Anthropic reports [an 84% reduction in permission prompts](https://www.anthropic.com/engineering/claude-code-sandboxing) from exactly this substitution. Every prompt you can delete this way is better than a prompt answered correctly, because it spends none of the user's attention.

## Human-in-the-loop that people don't rubber-stamp

Whatever survives rules, classifiers, and sandbox substitution reaches a human. Designing that moment is a usable-security problem with decades of prior art, and the headline finding is that the details of presentation dominate. The classic field study — Akhawe and Felt's ["Alice in Warningland"](https://www.usenix.org/conference/usenixsecurity13/technical-sessions/presentation/akhawe) (USENIX Security 2013), drawing on over 25 million browser warning impressions — found users clicked through 70.2% of Chrome's SSL warnings but only about a tenth to a quarter of malware warnings, depending on browser. Same users, same browsers, wildly different outcomes: warning *design* — frequency, clarity, perceived false-positive rate — determines whether a confirmation dialog is a control or a reflex. An agent harness that prompts forty times an hour is training its user to press approve, and a trained-to-approve user is worse than no gate at all, because the audit log now says a human reviewed it.

The design principles that follow:

**Ask rarely, so asking means something.** Every prompt eliminated by an allow rule, a sandbox boundary, or a classifier raises the signal value of the prompts that remain. The 84% figure above is not a convenience metric; it is a security metric.

**Show the action, not a description of it.** The unit of review must be the exact diff, the exact command, the exact URL — not the agent's summary of what it intends, which is model output and inherits all of model output's failure modes. A human shown `git push origin main --force` can catch what a human shown "syncing changes upstream" cannot.

**Tier by consequence.** Read-only operations shouldn't prompt at all (Claude Code ships a built-in read-only command set that never prompts). Reversible writes inside the workspace can batch or auto-accept. The full-attention prompt is reserved for the irreversible and the boundary-crossing: pushes, deploys, deletions, credentials, money. If everything warrants a prompt, nothing does.

**Scope "don't ask again" as narrowly as the approval.** A user approving `git status && npm test` is approving those commands — so persist per-subcommand prefix rules, not a wildcard covering whatever the full string happened to be. Persisted approvals are permission rules the user wrote under time pressure; the harness must make the cheap gesture safe rather than punishing it later.

**Move review upstream where it compounds.** A human who approves a *plan* — Chapter 9's orchestration patterns make plans first-class artifacts — has context for every action that implements it, and plan-then-execute (per the design-patterns paper above) means injected content encountered during execution can no longer rewrite what was approved. One considered review of intent beats fifty reflexive reviews of mechanics.

## Trust boundaries between agents

Multi-agent systems (Chapter 9) multiply the surfaces, and the same discipline applies between agents as between agent and world: a trust boundary is only real if it is enforced by the harness, not by politeness.

Three rules cover most designs. First, **a subagent's output is untrusted input** to whoever reads it. A quarantined agent that summarizes web pages has been exposed to injection by construction; if its prose is pasted into a privileged agent's context, the quarantine accomplished nothing — the injection rides the summary across the boundary. The Dual-LLM discipline of passing data *by reference* (typed values, schema-validated fields, opaque handles) rather than as free text is what makes the boundary real. Second, **capabilities must not be transitive**: the orchestrator's credentials and tool set do not flow to workers by default; each subagent gets the least-privilege set for its role, enforced by its own sandbox and permission profile, so a compromised log-reader in Ledgerbot's pipeline holds no push credential to abuse. Third, **generators must not touch their evaluators' environment**. Chapter 10 develops why verification belongs in a fresh context; the security reading is that an agent being graded has an incentive-shaped opportunity to pre-position state that fools the grader, and the only robust answer is the two-environment split — the evaluator sees the artifact, never the workspace that produced it.

## The tool supply chain

Every tool definition an agent loads is code you are running — and, uniquely to this ecosystem, *prose you are executing*, because tool descriptions enter the model's context as instructions. MCP made tool integration cheap and composable; it thereby made tool *trust* the weakest link, and 2025 supplied the case studies in rapid succession.

Invariant Labs [named the foundational attack in April 2025](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks): **tool poisoning**, malicious instructions embedded in a tool's description — visible to the model, typically hidden from the user's UI — that redirect the agent's behavior whenever the tool catalog is loaded. Their demonstrations included exfiltrating WhatsApp chat histories through a poisoned server, and two variants that break naive review: the **rug pull**, where a server serves a benign description at approval time and swaps in a malicious one later, and **tool shadowing**, where one malicious server's descriptions manipulate how the agent uses *other, trusted* servers in the same context. The class is now formalized as [MCP03 in OWASP's MCP Top 10](https://owasp.org/www-project-mcp-top-10/2025/MCP03-2025%E2%80%93Tool-Poisoning). It also measures badly for the defense: the [MCPTox benchmark](https://arxiv.org/abs/2508.14925) ran 1,312 poisoning cases against 20 agents across 45 real MCP servers and reports attack success rates above 60% for capable models (72.8% against o1-mini), with refusal rates under 3% — models don't recognize poisoned descriptions as attacks; they follow them as instructions, and more capable models follow them more competently.

Then came the conventional supply-chain compromise, arriving exactly on schedule. In September 2025, [Koi Security found `postmark-mcp`](https://www.koi.ai/blog/postmark-mcp-npm-malicious-backdoor-email-theft) — an npm package impersonating the Postmark email service's MCP server, built up over fifteen legitimate-looking releases and then, in version 1.0.16, given a one-line change that BCC'd every email sent through it to an attacker domain ([The Register's report](https://www.theregister.com/2025/09/29/postmark_mcp_server_code_hijacked/) covers the timeline). Roughly 1,500 weekly downloads; the first publicly documented malicious MCP server in the wild. Nothing about the attack was novel — it is typosquatting plus a backdoor, npm's oldest story — which is precisely the point: MCP servers are dependencies with an agent attached, and they inherit the entire package-ecosystem threat model *plus* the prose-execution channel.

The defenses are correspondingly two-layered. Treat servers as dependencies: install from vetted sources, pin versions, review what you run — and prefer platform-level control, like Claude Code's managed MCP allowlists (`allowManagedMcpServersOnly`) and deny rules such as `"mcp__*"` with per-server exceptions, so an individual developer's `npx some-mcp-server` habit is not your org's perimeter. Treat descriptions as attack surface: hash the full tool catalog at approval time and re-verify on every session, so a rug pull becomes a detectable diff rather than a silent swap; render full descriptions to the approving human; and scan them — Invariant's [MCP-Scan](https://invariantlabs.ai/blog/introducing-mcp-scan) exists for exactly this. And behind both layers, assume failure and fall back to the trifecta: a poisoned tool inside a no-egress sandbox with least-privilege tokens is an incident report; the same tool with a broad token and open network is a breach.

## Audit logging: the accountability layer

Every mechanism in this chapter eventually fails somewhere, and when it does, the questions are forensic: what did the agent read, what did it do, who approved it, and what left the boundary? The harness is the only component positioned to answer, because it mediates every model call and every tool execution. Chapter 11 develops the transcript as the debugging substrate; here it is the security record, and three additions turn a debugging transcript into an audit log.

Log *decisions*, not just actions: for each tool call, record which rule matched (and from which settings scope), the classifier's verdict and stated reasoning, and the human's response with the exact content they were shown — because "a human approved this" is only meaningful evidence if you can reproduce what they saw. Log at the *boundary*, not just in the loop: the egress proxy from Chapter 7 sees actual bytes leaving, which the agent-side transcript cannot prove; a transcript that says `git push origin fix-branch` and a proxy log that shows a push to a different remote is an incident detector. And make the log an asset, not a liability: it will inevitably capture secrets that transited the context, so redact on write, store with tighter access than the systems it describes, and ship it append-only off the host the agent can touch — an audit trail the subject of the audit can edit is theater. Done properly, the log closes the loop this chapter opened: prompt injection means you cannot always prevent the bad action, the sandbox and permission layers mean the bad action is bounded, and the audit layer means it is *seen* — which is, in the end, what turns an agent you hope is safe into one you can defend running.
